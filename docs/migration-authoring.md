# Migration authoring standards

This document is the production-grade checklist for authoring SQL
migrations consumed by `keystone-manager`. Migrations that pass this
bar produce zero linter warnings, integrate cleanly with the Plan-Gate-
Apply lifecycle, and remain rollback-safe across multi-tenant
deployments.

The 5 standards below are mandatory for tier-1 deployments. Each was
distilled from real findings on the example-service v0.1.13 e2e bundle that
landed today (2026-05-02). Skip any one and the linter rejects the
bundle at admission via the `MigrationBundleValidator` webhook OR the
`SchemaPolicy` analyzer flags it post-merge.

Applies to `MigrationBundle.spec.source.type` ∈ `{ConfigMap, Git, OCI}`
emitting `*.up.sql` files with the versioned strategy. Operations-
based bundles (`spec.operations`) follow a different path documented
in `docs/migration-operations.md` (roadmap).

---

## 1. Generate `keystone.sum` for integrity verification

Every migration directory MUST include a `keystone.sum` file alongside
the `*.up.sql` / `*.down.sql` pairs. The file is a manifest of
SHA-256 digests that `keystonectl` and the in-cluster reconciler
verify before applying any migration.

```bash
cd path/to/migrations/
keystonectl sum .       # writes keystone.sum
git add keystone.sum
```

The reconciler refuses to apply a bundle whose `keystone.sum` doesn't
match the live SQL files — this catches:

  - Accidental edits to a migration file after it was committed
    (migrations are immutable by contract; edit a new file instead).
  - Supply-chain tampering between Git and the cluster (a bad actor
    who can write to the ConfigMap source can't forge new digests
    without also rewriting `keystone.sum`).
  - Truncated transfers (zero-byte files from a broken ConfigMap
    apply).

`keystonectl sum` is idempotent — running it twice in a clean tree
produces byte-identical output. Diff the file in code review the same
way you'd diff `go.sum`.

## 2. `SET LOCAL statement_timeout = '30s'` per file

Every `*.up.sql` and `*.down.sql` MUST start with:

```sql
SET LOCAL statement_timeout = '30s';
```

The reconciler's runner already wraps each file in a transaction with
its own statement_timeout default (configurable per `DatabaseProvider`
spec, defaulting to 5 minutes). Adding `SET LOCAL` per-file is
explicit-rather-than-implicit:

  - A reviewer sees the timeout intent at the top of every file —
    they don't have to remember the cluster default.
  - Per-file overrides are possible (a heavy index build legitimately
    needs `SET LOCAL statement_timeout = '15min'` on JUST that file;
    the reviewer sees the deviation).
  - When the same migration runs against a different cluster (staging
    vs prod), the timeout is portable — not coupled to the cluster's
    DatabaseProvider spec.

The 30s default catches `CREATE INDEX` on a 100M-row table that
forgot `CREATE INDEX CONCURRENTLY`. That mistake should fail fast in
code review (with `EXPLAIN`), not blast a production lock.

## 3. `GENERATED BY DEFAULT AS IDENTITY` not `SERIAL`

Use SQL-standard identity columns:

```sql
-- DO
CREATE TABLE keystone_e2e_test (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    ...
);

-- DON'T
CREATE TABLE keystone_e2e_test (
    id BIGSERIAL PRIMARY KEY,
    ...
);
```

`SERIAL` is a PostgreSQL-specific shorthand that:

  - Creates an implicit sequence owned by the database (not the table)
    — schema dumps recreate the sequence in the wrong order, drifting
    backups subtly.
  - Doesn't survive `pg_dump --schema-only` cleanly across major
    PostgreSQL versions (sequences moved under tables in 10+).
  - Conflicts with multi-tenant patterns where tenants run their own
    isolated sequences with non-`int4` IDs.

`GENERATED BY DEFAULT AS IDENTITY`:

  - Is SQL-standard (works on any standards-compliant engine for
    future portability).
  - Owns the sequence on the column, not on the database — clean
    drop semantics on `DROP TABLE`.
  - Allows explicit overrides (`INSERT ... DEFAULT` works, but so
    does `INSERT INTO t (id, ...) VALUES (42, ...)` for testing).
  - `BIGINT` instead of `INT4` avoids the well-known integer-overflow
    incident class for tables that grow past 2.1B rows.

Use `GENERATED ALWAYS AS IDENTITY` only when you want to lock out
manual ID inserts (rare; overrides become OVERRIDING SYSTEM VALUE).
The `BY DEFAULT` form is the right choice for almost all cases.

## 4. No explicit `public.` prefix on table names

WRITE schema-relative DDL:

```sql
-- DO
CREATE TABLE keystone_e2e_test (...);
CREATE INDEX idx_kss_seq ON keystone_e2e_test(seq);

-- DON'T
CREATE TABLE public.keystone_e2e_test (...);
CREATE INDEX idx_kss_seq ON public.keystone_e2e_test(seq);
```

The reconciler runs every migration with `SET search_path = <target>,
pg_catalog` where `<target>` is the `DatabaseSchema.spec.name`. That
is:

  - For tenant `acme-corp`'s control schema, `search_path = acme_corp,
    pg_catalog`.
  - For example-service-public, `search_path = public, pg_catalog`.
  - For example-service-control-public, also `public` (it's in a different
    DATABASE so `public` doesn't collide).

Hardcoding `public.` defeats this. A single migration file is then
non-portable across schemas: it always lands tables in `public`,
even when the operator targeted a tenant schema. This breaks the
multi-tenant model that Phase 4.2 relies on.

The exception is when you NEED to reach across schemas — e.g., a
trigger that references `audit.events`. Spell it explicitly there
(`audit.events`) and document why in a comment. Bare `public.`
prefixes on the migration's own tables are always wrong.

## 5. Pair every `*.up.sql` with `*.down.sql`

For every `001_create_users.up.sql` there MUST be a
`001_create_users.down.sql` in the same directory. The down file
reverses the up file's effects — `CREATE TABLE` → `DROP TABLE`,
`ALTER TABLE ADD COLUMN` → `ALTER TABLE DROP COLUMN`, etc.

```sql
-- 001_create_users.up.sql
SET LOCAL statement_timeout = '30s';

CREATE TABLE users (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email TEXT NOT NULL UNIQUE,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_users_email_lower ON users(LOWER(email));
```

```sql
-- 001_create_users.down.sql
SET LOCAL statement_timeout = '30s';

DROP INDEX IF EXISTS idx_users_email_lower;
DROP TABLE IF EXISTS users;
```

The down file is the rollback path the reconciler uses when:

  - A subsequent migration in the SAME bundle fails — every preceding
    file in that bundle is rolled back via its `*.down.sql`.
  - An operator manually triggers `keystonectl rollback <bundle>` to
    reverse a deployment.

Down files MUST use `IF EXISTS` for `DROP` statements — partial
rollbacks (where only N of M up-statements ran) need to be idempotent.
Without `IF EXISTS`, the rollback fails on missing objects and leaves
the database in a worse state than before.

If a migration is genuinely irreversible (`DROP TABLE x` of a table
with 1B rows where re-CREATE would be impractical), the `*.down.sql`
SHOULD still exist with a single line:

```sql
-- 042_drop_legacy_orders.down.sql
SELECT 'irreversible: see migrations/042_drop_legacy_orders.md for archive procedure' AS rollback_note;
```

The empty-but-explicit down file makes the irreversibility visible
in code review and prevents the rollback orchestrator from
silently failing on a missing file.

## CI integration

Example Service's `hack/sql-lint` (added in example-service !97 after the 2026-05-01
oauth_client_columns whitespace bug) checks all 5 standards above
against every migration in the project. Run locally before commit:

```bash
make sql-lint        # in example-service; lint output is human-readable
```

Keystone's analyzer runs cluster-side against every MigrationBundle
on admission. Findings appear in `MigrationPlan.status.findings`
and operators see them via:

```bash
kubectl -n keystone-system get migrationplan <bundle>-<version>-<schema>-plan \
    -o jsonpath='{.status.findings}'
```

Linter findings DO NOT block the bundle in `validationFailureAction:
Audit` mode — they're advisory. In `Enforce` mode (recommended for
prod) any non-empty findings list rejects the bundle. Promote your
SchemaPolicy to Enforce only after a reasonable audit window (≥7 days
on staging).

## Authoring workflow

### Recommended: generate from a desired schema

`keystonectl migrate diff` authors a bundle that satisfies all five
standards above **by construction** — statement_timeout header, leading
comment, schema-relative DDL, `IF EXISTS` reverses, and a paired down
file. Edit your desired schema (a `SchemaDefinition`, a `.sql` file, or an
ORM export — see [migration-from-code.md](migration-from-code.md)), then:

```bash
keystonectl migrate diff add_users_created_at_index \
    --desired yaml://schema.yaml \
    --dev-url postgres://localhost:5432/devdb \
    --dir migrations
# → writes migrations/00N_add_users_created_at_index.{up,down}.sql + keystone.sum
git add migrations && git commit -m "feat: add users.created_at index" && git push
```

To onboard an existing database, [`keystonectl scaffold`](scaffold-from-db.md)
emits a baseline plus the full resource set.

### Manual

Hand-authoring is still supported when a change needs SQL the differ
cannot express (data migrations, conditional logic):

```bash
# 1. Author up + down with the statement_timeout header in the dir.
$EDITOR migrations/00N_my-change.up.sql migrations/00N_my-change.down.sql

# 2. Lint locally.
make sql-lint

# 3. Re-generate keystone.sum (CI does this too if you forget).
keystonectl sum migrations

# 4. Commit + open MR.
git add migrations && git commit -m "feat(example-service): backfill users.tier" && git push
```

The MR template in example-service pre-fills the migration checklist; check
each item before marking ready-for-review.
